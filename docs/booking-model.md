# Модель данных Pet Hotel (КР2–КР3)

Система для персонала гостиницы. Хозяева питомцев в систему не входят: `Owner` — это данные, не учётная запись.

## Основная сущность — бронирование (`Booking`)

| Требование ТЗ | Поле | Комментарий |
|---|---|---|
| UUID | `id UUID` | ключ в адресах API |
| Внешний код | `code`, например `BK-2026-0042` | уникальный, понятен человеку, используется при импорте CSV в режиме обновления |
| Основные поля | `pet`, `start_date`, `end_date`, `comment` | |
| Связь со справочником | `enclosure` | вольер |
| Статус | `status`: PENDING, ACCEPTED, DENIED, CANCELLED, COMPLETED | переходы — `BookingStatus.canTransitionTo` |
| Числовой показатель | `total_price NUMERIC(10,2)` | считается один раз при создании брони и хранится как снимок (см. ниже) |
| Логический признак | `special_care BOOLEAN` | нужен особый уход; влияет на стоимость |
| Теги | таблица `booking_tags` | метки без влияния на расчёты: «лекарства», «экзотический», «первый визит» |
| Вычисляемый показатель | `stage` — не хранится | см. ниже |
| Даты | `created_at`, `updated_at` | |
| Конкурентное изменение | `version` | 409 при несовпадении |
| Архив | `archived`, `archived_at` | архив вместо удаления |

### Стоимость

`total_price = цена за сутки × число дней`, при `special_care` — наценка (константа в сервисе, например 20%).
Считается при создании брони и записывается в неё. От тарифа после этого не зависит:
изменение цены не меняет уже созданные брони и аналитику по ним. Тип в Java — `BigDecimal`.

Источник цены за сутки — **решить**: таблица тарифов по размеру вольера (`tariffs: size, daily_price`)
или колонка `daily_price` у вольера.

### Стадия (`stage`) — вычисляемый показатель

| Стадия | Условие |
|---|---|
| `UPCOMING` | ACCEPTED, `start_date > сегодня` |
| `IN_HOTEL` | ACCEPTED, `start_date <= сегодня <= end_date` |
| `FINISHED` | ACCEPTED или COMPLETED, `end_date < сегодня` |
| `NOT_APPLICABLE` | PENDING, DENIED, CANCELLED |

Зависит от текущей даты, поэтому **не хранится колонкой** (устаревала бы каждый день).
В ответе API считается в маппере; серверный фильтр по стадии переводится в условие на статус и даты.

## Справочная сущность — вольер (`Enclosure`)

Номер, размер, признак `active` (вольер на ремонте — отключён, не удаляется).
Список доступен всем ролям, изменение и включение/отключение — только администратору.

## Пользователи и роли

| Роль | Кто | Права |
|---|---|---|
| `VIEWER` | смотритель, ветеринар | просмотр |
| `MANAGER` | менеджер | создание и изменение броней, заметки |
| `ADMIN` | администратор | вольеры, пользователи, аудит, окончательное удаление |

Регистрации нет. Первый администратор создаётся при старте из `.env` (`BOOTSTRAP_ADMIN_*`)
с временным паролем, остальных создаёт администратор. Временный пароль обязательно сменить при первом входе.

## Остальное по ТЗ КР3

Заметки к брони (автор, время, закрепление), refresh-сессии, журнал аудита — отдельные таблицы.
Все изменения схемы — миграциями Flyway, `ddl-auto=validate`.
